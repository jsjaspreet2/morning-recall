Runs Over Text

Drill figma-04-styled-text-ranges: what a "style range" is, what slicing does to one, and why applying a style is a three-way split followed by a merge. Drag the range below and watch the runs rebuild.

0Styles are not on the characters

The naive model gives every character its own style object. It is correct and it is what you must not build: a paragraph of ten thousand characters becomes ten thousand objects, and "is this whole selection bold" becomes a scan. The model every real editor uses is runs — half-open intervals over the string, each carrying one style.

type Style = Readonly<Record<string, string | boolean>>type Run   = { start: number; end: number; style: Style }   // [start, end)

Ask about half-open versus inclusive in the first minute, and if they do not care, say you are taking half-open and why: end - start is the length, an empty run is start === end, and adjacency is a.end === b.start with no + 1 anywhere. That single choice removes about half the off-by-ones this problem has available.

1The invariant is the answer

Four clauses. Say them before you write a line, put them in one function, and call that function at the end of everything. Every bug in this problem is one of these four being violated somewhere that no single function owns.

The trap is inlining the merge into applyStyle "since it's only three lines". Then sliceStyled grows its own slightly different notion of adjacent, and the two disagree on exactly one case — usually the empty run — six minutes before the hour ends.

2The live model

The bar under the characters is the range [from, to). Everything below recomputes from it as you drag.

Part 1Slice: clip, then rebase

Slicing is two ideas that must happen in that order. Clip each run to the window — max(r.start, from) and min(r.end, to) — and drop it if nothing survives. Then rebase: the returned runs index into the new string, so subtract from from both ends.

for (const r of runs) {  const start = Math.max(r.start, from)  const end   = Math.min(r.end, to)  if (start < end) out.push({ start: start - from, end: end - from, style: r.style })}return { text: text.slice(from, to), runs: normalize(out) }

Forgetting the rebase is the classic failure, and it hides: the first test people write slices from 0, where start - from and start are the same number. Write the "slice from the middle of one run" test first instead — it fails on both the rebase and the clip.

Part 2Apply: split three ways, then merge

An overlapped run becomes up to three pieces: the part before the range keeps its style, the overlapping part gets the patch, the part after keeps its style. A single run needs all three at once when the range sits strictly inside it — test that case first, it is the one that fails.

Runs that do not overlap the range at all are pushed through untouched, in one branch, before any of this. Two ifs and a push, in that order.

if (from >= to) return runs                              // empty range: a no-op, not an errorfor (const r of runs) {  const lo = Math.max(r.start, from), hi = Math.min(r.end, to)  if (lo >= hi) { out.push(r); continue }                // no overlap  if (r.start < lo) out.push({ start: r.start, end: lo, style: r.style })  out.push({ start: lo, end: hi, style: { ...r.style, ...patch } })  if (hi < r.end) out.push({ start: hi, end: r.end, style: r.style })}return normalize(out)                                     // the only place merging happens

3Patch, not replace

{ ...r.style, ...patch } and patch are one keystroke apart and are different features. Applying italic to text that is already bold should give bold italic; replacing would silently strip the bold. Ask which they want — it is one of the three opening questions — and then make the code say the answer.

5Say it out loud

"Text is a string plus runs — half-open intervals, sorted, contiguous, non-empty, and no two neighbours carrying the same style. That invariant lives in one normalize function and everything calls it on the way out."
"Slice clips each run to the window and then rebases it, because the returned runs index into the new string, not the old one."
"Applying a style is a three-way split — keep left, patch middle, keep right — and then a merge pass. A range strictly inside one run is the case that needs all three, so that's the test I'll write first."
"I'm treating the style as a patch rather than a replacement, so applying italic to bold text gives both. If you want replace semantics it's one spread to delete."

And the follow-up they reach for when you finish early: "what does this cost?" Both functions are O(n) in the number of runs, not the number of characters — which is the entire reason for the model. If the runs were not guaranteed sorted you would sort first, at O(n log n), and you should say which you are assuming.
