0One array does two jobs

A layer tree is nodes with a parent and an ordered list of children. The order is not incidental — it is the z-stack. Rendering is a depth-first walk that paints leaves in that order, so "later in the array" and "in front on the canvas" are the same statement.

type TreeNode = { id: Id; parent: Id | null; children: Id[] | null }   // null children = leaf

what a renderer draws

Painted bottom of the stack first, so the last leaf in the walk is the one on top.

Ask which end is the top, and then say your answer out loud even if they shrug. This page uses children[0] = bottom of the stack, matching the paint order of a DFS. Get the convention backwards silently and everything still runs, every test you write yourself still passes, and the canvas is inverted.

1Where a new group lands

This is the question interviewers wait for, and it has a conventional answer: the group takes the slot of its topmost member. The reasoning is what earns the point — a group must not fall behind anything it was previously in front of, because in a design tool that is a canvas change the user did not ask for.

Live Group under three slot policies.

Two things the live panel shows that the one-line rule hides. First, when the members are adjacent, "topmost" and "bottommost" are the same slot — a contiguous block has one hole, and the group goes in it. Any test built only on adjacent members grades both as correct, so it does not test the rule at all. Second, when the members are not adjacent, no policy can leave the canvas alone: pulling r1 and r3 into one group has to move r2 either behind both or in front of both. Topmost moves the in-between layers back; bottommost moves them forward. Saying "this case can't be order-preserving, here is the trade I'm making" is a stronger answer than a rule recited without its edge.

3Reparenting into your own subtree

Two lines guard it and they are the check the interviewer is hoping you write before being asked. Move a node under one of its own descendants and the structure stops being a tree: the cycle is unreachable from the root, so nothing looks broken until a traversal enters it and never leaves.

Walking up from newParent through parent pointers is O(depth) and three lines, and it is the same check Figma's own servers run before accepting a parent update. Reject; do not repair.

And: remove before you insert
const at = to.indexOf(ref)          // computed BEFORE the removalfrom.splice(from.indexOf(id), 1)to.splice(at, 0, id)               // stale by one when from === to

When the source and destination parents are the same array, an index computed before the removal is one too large for everything after the hole. It is right in every cross-parent test and wrong in every reorder-within-a-parent test, which is a debugging session you can skip by never holding an index across a mutation.

5Say it out loud

"Nodes have a parent and an ordered child list, and that order is the z-stack — children[0] is the bottom. Leaves have children: null so a leaf and an empty group are different things."
"A new group takes the slot of its topmost member, so the canvas doesn't change. Members keep their relative order read off the parent, not off the ids array the caller passed, which is probably in selection order."
"Before I reparent I'm walking up the parent pointers to check the new parent isn't a descendant. It's O(depth) and it stops the tree becoming a graph — otherwise the corruption is silent until some later traversal hangs."
"Ungroup is one splice: remove the group and insert its children at that same index, so the stack is unchanged. And I update the children's parent pointers in the same step, because a node whose parent pointer lies is worse than one that's missing."

If they ask for complexity: group and ungroup are O(siblings), reparent is O(siblings + depth), paintOrder is O(nodes). Nothing here should be quadratic, and if yours is, it is an indexOf inside a loop.
