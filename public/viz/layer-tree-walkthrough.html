Layer Tree Drill 5, played through

State the convention before you type

A layer document is a tree where sibling order is z-order. Every method here is a list splice plus a parent-pointer update; the whole grade is whether the splice lands in the right slot.

The node

type TreeNode = {
  id: Id
  parent: Id | null
  children: Id[] | null   // null = leaf
}
nodes = new Map<Id, TreeNode>()

Ids, not object references, so parent and child pointers can't drift apart. A leaf has children: null, which makes "is this a container" a one-field check.

The convention

children[0]  → BOTTOM of the z-stack
children[n]  → TOP

paintOrder = leaves, depth-first,
             bottom first

Say it out loud. The layers panel in this walkthrough shows top first, like Figma; the array is the reverse. Getting this backwards silently is how you fail your own test.

The answer interviewers wait for: "A new group takes the slot of its topmost member, and the members keep the relative order they had in the parent, not the order the caller passed in. Any other placement changes what the canvas looks like, which is a correctness bug in a design tool, not a preference."

Three rules that cover the rest

  • Remove before you insert. Never reuse an index computed before a removal; the removal shifts everything after it.
  • Write the cycle check before they ask. Reparenting a node under its own descendant makes something that is no longer a tree; every later traversal hangs. Walking parent pointers is O(depth) and three lines.
  • Ungroup is one splice. siblings.splice(at, 1, ...group.children) removes the group and inserts its children in the same slot.

What to say out loud

Group, in one pass over the parent

const top = Math.max(...ids.map(id => siblings.indexOf(id)))
const next = []
siblings.forEach((cid, i) => {
  if (members.has(cid)) { if (i === top) next.push(groupId); return }
  next.push(cid)
})
const ordered = siblings.filter(cid => members.has(cid))   // order from the PARENT

"One walk over the parent's children: skip members, drop the group where the topmost member was, keep everything else. The group's children are the members filtered out of the parent, so the caller's selection order never matters."

The non-adjacent case

If the members aren't contiguous, no policy can leave the canvas untouched: something between them has to end up above or below the whole group. Topmost-slot is the choice that keeps the top member where it was and pulls the lower members up to meet it. Say that you know this, and that the alternative (bottommost slot) pushes the top member down instead.

Ungroup does not undo group

Ungroup splices the children back where the group sits, not where they came from. After grouping non-adjacent layers and ungrouping, the canvas matches the grouped state, not the original. That's correct: ungroup should never change the picture either.

Reparent: the index semantics

from.splice(from.indexOf(id), 1)                      // remove first
to.splice(Math.max(0, Math.min(index, to.length)), 0, id)   // then clamp and insert

"I interpret the index after the removal. Moving within the same parent is the only case where that differs from pre-removal indexing, and it's the case a real drag hits constantly, so I'm naming it." Starting [a,b,c,d,e], reparent('a', root, 3) gives [b,c,d,a,e]; the other reading gives [b,c,a,d,e]. Both are defensible; unstated is the failure.

The cycle check

isAncestor(maybe, of) {
  let cur = nodes.get(of)?.parent ?? null
  while (cur !== null) { if (cur === maybe) return true; cur = node(cur).parent }
  return false
}

Two guards at the top of reparent: id === newParentId, then isAncestor(id, newParentId). Figma's own servers reject parent updates that would create a cycle. Mention it unprompted.

Complexity, one line

Group and ungroup are O(siblings). Reparent is O(depth + siblings). Everything is index-based on small arrays; a linked sibling list would make the splices O(1) at the cost of a much larger surface, which is the trade you'd name if asked to scale.
