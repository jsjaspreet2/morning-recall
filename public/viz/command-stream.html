0The skeleton, which is every drill in this folder

Text in, data out, one function that mutates, and then a query layer that touches neither. If the method only works on problems you have seen before, it is not a method — this is the shape to fall back on when the interviewer hands you something nobody has reported.

type Op = { kind: 'set'; key: string; value: number }        | { kind: 'add'; key: string; delta: number }        | { kind: 'clear' }parse(line): Op                    // text → data, and the ONLY place text existsstep(state, op): void              // the only thing that mutatesstateAt(n): State                  // built on the two above, changing neither

Parsing into a discriminated union rather than keeping strings around is what makes step a switch the compiler can check for exhaustiveness. When they add a fourth command in part 3, the type error tells you every place that needs updating — say that out loud when you write the union, because it is the reason for it.

Part 2"What was the state after the first n commands?" — many times

Answering once is a replay. Answering repeatedly is where the question actually is, and it has two useless extremes and a family of answers in between. Say the extremes first; they define the axis you are trading on, and stating them takes fifteen seconds.

The middle is a checkpoint every k ops. A query jumps to the nearest checkpoint at or before n and replays at most k − 1 ops from there. Drag both sliders and watch the highlighted span.

3The two curves cross, and that is the whole answer

Worst-case replay grows with k. Snapshots kept shrink with k. They are in different units — one is ops, one is copies of the state — so there is no universally optimal k; there is an optimal k once you say how big the state is relative to an op. That sentence is the graded content of part 2.

Drag the stride slider above; the marker moves. k ≈ √n balances the two counts, which is the answer to give when they do not specify a state size — and then immediately say what would move it: "if the state is large relative to an op I'd push k up and replay more; if replaying is expensive — say each op hits the network — I'd push it down and keep more snapshots."

4The copy, and the clamp

stateAt must return a copy
const state = new Map(base.state)   // callers must not corrupt a checkpoint

Hand back the checkpoint itself and the first caller who mutates the result silently rewrites history for every later query. It is one new Map, and it is the difference between a cache and a landmine.

clamping, both ends

A query index comes from a scrubber or a URL. Clamping is the behaviour a caller can use; throwing on n = 999 means every caller writes the same Math.min you could have written once.

5Say it out loud

"Parse into a discriminated union first, so the only place strings exist is parse. Then one step function that mutates, and everything else composes it."
"For repeated queries: a snapshot per op is instant and unusable, no snapshots is free and O(n) per query. I'll checkpoint every k ops — a query replays at most k−1 and memory is n/k copies of the state."
"k ≈ √n balances the two. The right k really depends on how big a state copy is compared to replaying one op, so if you tell me the state is a hundred keys and ops are cheap, I'd raise k."
"stateAt returns a copy — otherwise a caller mutating the result corrupts the checkpoint everyone else replays from."

And the extension worth naming before they ask: appending is O(1) amortised here, but only because a checkpoint is taken on a stride boundary rather than recomputed. If the log could be edited in the middle rather than only appended to, every checkpoint after the edit is invalid — which is the point where you would reach for a persistent data structure instead of snapshots.
