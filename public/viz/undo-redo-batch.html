0What part 2 adds is three fields and one function

If part 1 was built with a single commit() choke point and a stack of Commit = Change[], then redo and batching land almost entirely inside that one function. set, get, createLayer, deleteLayer and applyChange do not change at all.

part 1
private commit(change: Change) {  this.applyChange(change)  this.undoStack.push([change])}
part 2 & 3
private commit(change: Change) {  this.applyChange(change)  if (this.batch) { this.batch.push(change); return }  this.undoStack.push([change])  this.redoStack.length = 0}

Two added lines. That is the whole payoff of the part-1 design, and saying it out loud as you type the second version is worth more than the code: "both new features land in the same function, which is why I put the choke point in earlier."

1Undo reverses twice; redo does not reverse at all

A batch is a list of changes in one stack entry. To undo it you must reverse the order of the list and invert each change in it. To redo it you walk the list forward, applying each change as recorded. Get one of those two reversals wrong and single-change commits still pass every test, because a list of one reads the same in both directions.

A batch that sets x, then y, then deletes a layer. Undo removes the layer's deletion first, then y, then x — the way you unwind a call stack. Redo replays them in the order they happened. The same list object moves between the two stacks; nothing is rebuilt.

3Why new work has to throw the redo branch away

History is not a line, it is a tree, and undo walks you back up it. If you then edit, you have created a second branch from that point. Keeping the old redo entries would mean pressing redo replays changes recorded against a document that no longer exists — before values that were captured in a world you have left.

Undo to the fork, then make a new edit. Every editor you have used discards the grey branch; almost none offer to keep it, because a redo tree needs UI nobody wants to build. Say that you know it is a product decision, not a technical necessity — that sentence is the difference between "implemented undo" and "designed undo".

Where the clear has to live

In one place: commit(), and its twin in commitBatch(). Put it in set() instead and the day someone adds reorderLayer() the redo stack survives a new edit, which is a corruption bug that reproduces only after a specific five-key sequence.

4The semantics are the question

Batching has no single correct answer, which is exactly why it is asked. Every row below is a decision you should state before you implement it — and the drill's tests encode one particular set, so if you pick differently, say so and the interviewer will grade the reasoning, not the match.

5The five invariants, checked live

These run in your browser against the reference implementation right now. In the room you would type three of them as asserts; the point is that they are statements about any sequence, not about one example.

Number five is the one to write first if you only write one: undo then redo returns the document to an identical state. It catches a wrong reversal direction, a lost before, an aliased map, and a redo that rebuilds instead of replays — four separate bugs, one assert.

6Say it out loud

"Redo is the same commit object moving back the other way. Undo pops undo and pushes redo; redo pops redo and pushes undo. Nothing gets recomputed, so they can't disagree."
"New work clears the redo stack, and I'm putting that clear in commit rather than in each method, so no future mutation path can forget it."
"A batch is one stack entry holding several changes. Undo reverses twice — the list, and each change in it. That's invisible with single-change commits, so it's worth a test of its own."
"For the edge cases I'm choosing: nested begin is ignored rather than counted, a stray commit is ignored, an empty batch is not an undo step, and undo mid-batch does nothing because the history is intermediate until the batch closes. If you'd rather nesting were reference-counted I can do that instead — it's a depth counter and one condition."

That last clause is the move: name your choice, give the alternative, price it. It converts an edge case from a thing you might have missed into a thing you decided.
