Undo as Data

Drill figma-01-document-undo: what the document actually is, why a change is a record and not a function, and what undo does to it. Every panel below runs the drill's reference code live in your browser.

0The document is two nested maps

"A document made of layers, each layer holds properties as key/value pairs" is one sentence, and it is already the data structure. There is no tree in part 1, no geometry, no ordering. There is a map from layer id to a map from key to value.

type PropValue = string | number | booleantype Props     = Map<string, PropValue>layers: Map<string, Props>

Say the shape out loud in the first two minutes. The interviewer is listening for whether you commit to a model before you start typing methods, because everything after this is determined by it.

1A change is (target, before, after)

The instinct is to store undo as a stack of functions — "to undo this, call set(a, 'x', 10)". Don't. Store data: what was touched, what it held, what it holds now. Then undoing is not a second code path. It is the same applyChange with two fields swapped.

invert is a swap, not a computation. There is no per-operation inverse to write, no unsetProperty, no uncreateLayer. That collapse is what makes redo and batch rollback nearly free in drill 2 — and it is the single design point this drill is measuring.

undefined on either side means the key is absent. That one convention is why undo after the first set must delete the key rather than set it to undefined. get returns undefined either way, so a test on get alone will not catch it — the drill checks has.

3The copy that looks unnecessary

Two lines in the reference solution copy a props map instead of storing the one they were handed: deleteLayer records new Map(props), and applyChange restores with new Map(c.after). Both look like waste, and both are the line reviewers ask about.

before: new Map(props)   // history is a photographbefore: props            // history is a mirror

Here is the honest finding, and it is worth knowing before you defend the line in a room. With only the six methods this drill asks for, dropping both copies does not actually produce a wrong answer. I searched: every sequence up to thirteen calls drawn from createLayer, deleteLayer, set, undo and redo, and the aliased version agrees with the copying one every time.

The reason is structural, not luck. For an aliased map to do damage, a record must still be on a stack, hold a map by reference, have that map mutated, and then be applied. But the mutations sit above that record on the undo stack, so anything that reaches down to re-apply it has already reverted them — and new work after an undo clears the redo branch instead. The discipline that makes the history correct is the same discipline that hides the aliasing.

LiveNow add one method the interviewer is likely to ask for: duplicateLayer(src, newId).

The duplicate is not on any stack and is not reached through undo, so nothing reverts it. Two layers now share one Props object, and setting fill on the copy repaints the original. One new method, immediately fatal.

So the sentence to say is not "this would be a bug" — it would not be, yet. It is: "I'm copying on the way into history and on the way out, so a record is a snapshot and not a view. It costs a map copy per structural edit, and it means the next method someone adds can't quietly alias the document." That is a claim you can defend when they push, which the confident overstatement is not.

4What part 1 costs you in part 2

The drill's real question is not whether these tests pass. It is what your part 1 charges you when the interviewer says "now support redo", and then "now let me group operations into one undoable batch". Two decisions decide that, and both are cheap now and expensive later.

Neither costs you anything in part 1. A stack of Change[] where every entry happens to have length 1 reads the same, tests the same, and is one line different. That is the whole point of the drill — see the drill 2 page for what lands on top of it.

5Say it out loud

"The document is a map of layers, each layer a map of properties. I'm going to represent every edit as a record — target, before, after — because then undo is the same apply with the two fields swapped, and I get redo almost for free later."
"One convention: undefined on either side means the key is absent. So undoing the first set of a key deletes it rather than setting it to undefined — otherwise has starts lying."
"Every mutation goes through one private commit. If a second path to mutation exists, some future feature forgets to record history on it, and that bug is invisible until someone hits undo."
"Setting a property to the value it already holds isn't an undo step. Otherwise the user presses undo and nothing appears to happen, which reads as a broken button."

Then invite the follow-up rather than waiting for it: "The obvious next things are redo and batching — do you want me to take one of those, or harden this first?"
