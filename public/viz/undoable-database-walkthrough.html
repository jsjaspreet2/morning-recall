Undoable Database Drill 10, played through

Say the model before you type

Every undo/redo problem is the same machine: a history, two directions, and one choke point that decides what enters history. The only real decision is what a history entry is.

Snapshots

history: User[][]   // one full list per step
index:   number     // points at the live one

undo → index--
redo → index++

Copy the whole list on every edit. Undo and redo are index arithmetic; nothing is ever recomputed.

Inverse commands

history: { do(), undo() }[]
index:   number

undo → history[index--].undo()
redo → history[++index].do()

Store the edit and its reverse. Memory is O(1) per step, but every CRUD method has to know how to invert itself, and a delete has to remember position.

The sentence that is most of the grade: "This prompt is worded as snapshots and the record list is small, so I'll snapshot. That's O(n) per step in time and memory. When the list gets large I'd swap to inverse commands: the history code survives that swap, the three CRUD methods don't."

The one choke point

Each CRUD method computes the next list, or null when the call would change nothing (missing id, identical patch). Only a non-null list reaches commit. That single guard gives you three checklist items for free: no-ops aren't steps, no-ops don't clear redo, and the id can't change because the merge pins it: { ...user, ...patch, id: user.id }.

function nextUsers(users, op, id, payload): User[] | null {
  const i = users.findIndex(u => u.id === id)
  switch (op) {
    case 'add':    return [...users, { ...payload }]
    case 'update': if (i < 0) return null
                   const merged = { ...users[i], ...payload, id: users[i].id }
                   if (shallowEqual(merged, users[i])) return null
                   return users.map((u, j) => j === i ? merged : u)
    case 'delete': if (i < 0) return null
                   return users.filter((_, j) => j !== i)
  }
}

What to say out loud

Part 1 in one sentence

"Three CRUD methods each compute a next list or null, and route it through one commit: slice history to index + 1, push, index++. Undo and redo just move the index with bounds guards."

Part 2: three semantics that flipped from drill 2

QuestionDrill 2 (layers batch)Drill 10 (draft)
How does batching begin?Explicit beginBatch()Implicitly, on the first real edit after a commit
Undo inside the batch?IgnoredDiscards the draft; committed history untouched
When does redo die?At commitWhen the draft starts, before commit

The whole diff between the two classes lives in three places: edit (start the draft and slice history there), undo (draft pending means cancel), and commit (push without slicing, because the slice already happened).

private edit(next: User[] | null) {
  if (next === null) return
  if (this.draft === null) this.history = this.history.slice(0, this.index + 1)
  this.draft = next
}
commit() { if (this.draft === null) return; this.history.push(this.draft); this.index++; this.draft = null }
undo()   { if (this.draft !== null) { this.draft = null; return } if (this.index > 0) this.index-- }
redo()   { if (this.draft !== null) return; if (this.index < this.history.length - 1) this.index++ }

Two things the prompt leaves open: decide and say so

"commit() with nothing pending is a no-op, not a step. A CRUD call that would change nothing doesn't start a draft either. Both follow from the same null guard, and I'd confirm with the interviewer rather than assume."

Copy detail worth one sentence

getUsers returns users.map(u => ({ ...u })): a new array and new objects, so callers can't mutate history through the return value. The test mutates the returned object and asserts the store didn't change.
