0The problem

Objects on a canvas, each a box { id, x, y, w, h }. Origin top-left, y grows downward. Return them in the order a reader's eye takes them: row by row, left to right within a row. The output must be a permutation of the input: same length, same ids, nothing invented, nothing lost.

The five boxes are one visual row of three and a second row of two. The correct reading order is ABCDE. Notice that inside the top row, B sits higher than A even though A comes first. That single fact is the whole drill.

Part 1Aligned rows: sort by y, then by x

When rows are perfectly aligned, every box in a row shares the same y. So "reading order" is just a lexicographic sort on the pair (y, x): smaller y first, and when y ties, smaller x first.

function readingOrderAligned(boxes: Box[]): Box[] {  return [...boxes].sort((a, b) => a.y - b.y || a.x - b.x)}

a.y - b.y || a.x - b.x: the first difference is the answer unless it is 0, which is falsy, and then the second difference decides. [...boxes] copies first because sort mutates in place.

The drill's grid test. Input order is D, A, C, B. Sorted by (y, x): . Output . The numbered path snakes exactly the way a reader would.

The same sort on the misaligned row. y is compared as an exact number. B's top is 0 and A's is 4, so B is placed first. Output : the path jumps right, then back left. Part 1 has no concept of "a row"; it only has a number.

The trap"Same row if the tops are within 5"

The obvious patch is to soften the y comparison: treat two boxes as the same row when Math.abs(a.y - b.y) < 5, and compare x in that case.

// DO NOT SHIP THIS[...boxes].sort((a, b) => Math.abs(a.y - b.y) < 5 ? a.x - b.x : a.y - b.y)

"Within 5 of each other" is not transitive. A can be within 5 of B, B within 5 of C, and A not within 5 of C. That means the comparator sometimes decides by x and sometimes by y for boxes in the same visual row, and the two rules can disagree.

The staircase. Tops at 8, 4 and 0, with x increasing left to right. Visually one row; a reader says ABC.

Each edge shows which rule the comparator uses for that pair, and who it says comes first. Follow the arrows: A before B, B before C, C before A. A cycle. There is no order that satisfies all three, so sort is being asked a question with no answer.

Why the drill's own "tops at 0, 4 and 8" test is survivable. In that case x and y increase together (A is leftmost and highest), so the x-rule and the y-rule agree on every pair and there is no cycle. The comparator is still broken as a matter of principle, and the test still guards the right thing (the sweep must not care about the chain), but the visible damage needs x to run one way while y runs the other. If you want a test that fails a tolerance comparator outright, the staircase is it.

Part 2Group first, sort second: the sweep

The fix is to stop asking "are these two boxes in the same row?" and instead ask a question with running state: "does this box still overlap the row I am currently building?" A sweep is allowed to be non-transitive, because it never compares two boxes with each other. It compares one box against one number.

Three phases. Sort every box by its top edge. Sweep down the sorted list, tracking rowBottom, the lowest edge seen in the current row: a box whose top is at or below rowBottom starts a new row; otherwise it joins, and may push rowBottom further down. Then sort each row by x.

const byTop = [...boxes].sort((a, b) => a.y - b.y || a.x - b.x)const rows: Box[][] = []let rowBottom = -Infinityfor (const box of byTop) {  if (box.y >= rowBottom) rows.push([])  rows[rows.length - 1].push(box)  rowBottom = Math.max(rowBottom, box.y + box.h)}return rows.flatMap((row) => row.sort((a, b) => a.x - b.x))

Why the sweep survives the staircase and the chain. Sorted by top, the staircase is C(0), B(4), A(8). C opens a row and sets rowBottom to 10. B's top is 4, below 10, so it joins. A's top is 8, still below 10, so it joins. One row, then sorted by x: A, B, C. The sweep never asked whether A and C were "close". It asked whether each one started above the row's current bottom.

The stated limitation. Pick the Tall element scenario. T is 100 tall, so rowBottom jumps to 100 on the first step and everything beside T joins its row, including B at y=50. That is a defensible choice (a full-height sidebar arguably is beside everything), but say it before the interviewer finds it. The alternative, comparing against the first element's band instead of the running maximum, caps the damage at the cost of making the result depend on which box opened the row.

Say itWhat to say out loud at the Part 2 boundary

"The instinct is a tolerance in the comparator, but that isn't transitive: tops at 0, 4 and 8 make A~B and B~C but not A~C, and sort needs a strict weak ordering. So I'll group first and sort second. One pass down the boxes sorted by top, tracking the current row's bottom edge; a box joins if it overlaps, otherwise it starts a new row. Then left-to-right inside each row. The sort dominates at O(n log n); the sweep is linear."

"One thing to flag: a tall element merges the rows it spans, because I extend the band as I go. I'd want to know what these objects are before deciding whether that's right."
